# Verity AI: Fallback Fix + Provider/Model Pickers — Design

**Date:** 2026-08-10
**Status:** Approved

## Context

Verity's local-vs-remote AI is controlled per sidecar (Core LLM/Ollama, Voice out/Kokoro, Voice in/Whisper) via booleans in `verity-common.toml`, written/read through `_shared\scripts\verity-helpers.ps1`. The Verity mod's own factory default (generated by the mod itself on a server's first launch, confirmed against the untouched-looking `VerityCraft` instance) already ships remote/cloud-first (`aiProvider = "OPENAI"`, `ttsProvider`/`sttProvider = "NATIVE"`) — so nothing needs to change about new-server defaults; the mod already does the right thing for users who can't run local AI.

Two real gaps remain, found while auditing this for release:

1. **Fallback bug:** when a user has opted into a local sidecar (e.g. Ollama) and it fails to start, `start-with-tunnel.ps1:22-34` logs `Write-Warning "...will fall back to its configured cloud provider"` but never actually changes the toml — Verity mod-side keeps pointing at the dead local endpoint and silently doesn't work. The server still launches; the AI feature just doesn't.
2. **No provider/model choice:** the GUI's `VerityAiPanel` only exposes a local/remote toggle per sidecar plus a single API key field. The toml already supports choosing a remote LLM provider (`aiProvider`: GEMINI, GROQ, OPENROUTER, MISTRAL, OPENAI) and a local Ollama model (`aiModel`, currently hardcoded to `timheinrich2011/verity-3b` at the script level, not exposed at all in the UI) — there's no UI for either choice.

TTS/STT remote mode has no equivalent provider choice — `ttsProvider`/`sttProvider` only support `NATIVE` for remote (Kokoro/Whisper are the only local alternatives) — so no picker is needed there; this spec's provider dropdown applies to the Core LLM sidecar only.

## Goals

1. When a local sidecar fails to start, actually flip that sidecar's toml value to remote before the server launches, so the warning message's claim becomes true.
2. If a local sidecar fails AND no API key is configured, don't block the server — flip to remote anyway (config stays consistent) and let the Minecraft server start normally; Verity's own mod-side already handles a missing key without crashing the server.
3. Add a remote-provider dropdown (Gemini/Groq/OpenRouter/Mistral/OpenAI) to `VerityAiPanel`, next to the existing API key field.
4. Add a local-model dropdown for Ollama to `VerityAiPanel`. Ship with exactly one entry (today's hardcoded `timheinrich2011/verity-3b`) — the picker's plumbing exists now so adding more models later is a list edit, not new code.

## Components

### 1. `Set-VerityRemoteFallback` (new helper, `verity-helpers.ps1`)

Signature: `Set-VerityRemoteFallback -ConfigPath <string> -Sidecar <'Ollama'|'Kokoro'|'Whisper'>`. Flips the given sidecar's provider to remote in whichever schema the file uses (branches on the existing `Test-VerityOldSchema`, reusing `Set-TomlSectionValue`/`Set-TomlSectionBoolValue` exactly as `Set-VerityAiProvider` already does) — no new toml-writing primitive, just a new call site combining existing ones for the "one sidecar → remote" case. Never throws; a write failure here is best-effort (matches the project's established pattern) and doesn't block server launch — worst case the mod still sees the stale local value, which is the pre-existing failure mode, not a regression.

### 2. Fallback fix in `start-with-tunnel.ps1`

At the existing catch block around line 22-34 (where the `Write-Warning` currently fires after a sidecar start failure), add a call to `Set-VerityRemoteFallback` for that sidecar before continuing to server launch. No new conditional structure — same catch, one added line per the sidecar that failed.

### 3. Remote provider dropdown

`HomeScreen.xaml`: a `ComboBox` added to `VerityAiPanel`, styled to match the panel's existing card layout, positioned next to the API key text field. Options: Gemini, Groq, OpenRouter, Mistral, OpenAI (matches the toml's documented `Allowed Values` for `aiProvider`, excluding `OLLAMA` which is controlled by the existing local/remote toggle, not this dropdown).

`Start-Gui.ps1`: wire `SelectionChanged` to write `aiProvider` via the existing `Set-VerityAiProvider`-style path already used for the API key field's save action — same write pattern, new field.

### 4. Local model dropdown

`HomeScreen.xaml`: a `ComboBox` added to `VerityAiPanel`'s local/Ollama side, single entry: `timheinrich2011/verity-3b` (label matches the current hardcoded value verbatim).

`Start-Gui.ps1`: wire `SelectionChanged` to write `aiModel` (old schema) or the new-schema equivalent, same branching pattern as the provider dropdown. With one entry, this is inert today (writes the same value that's already hardcoded) — the point is the UI/write-path existing for when a second model is added later.

## Data Flow

**Fallback fix:** sidecar start attempt → timeout/failure (existing 30s-poll exception path) → catch block → `Set-VerityRemoteFallback` writes toml → `Write-Warning` (existing message, now accurate) → server launch proceeds unchanged.

**Dropdowns:** user selection → `SelectionChanged` → write to `verity-common.toml` (schema-branched, matching existing API-key-field pattern) → next sidecar start / server launch reads the updated value. No new read path — this reuses whatever already reads `aiProvider`/`aiModel` today.

## Error Handling

- `Set-VerityRemoteFallback` never throws (best-effort write, matching `Get-AppVersion`'s and other helpers' established pattern in this codebase).
- No API key + flipped to remote: Verity mod-side already handles a missing/blank key without crashing the Minecraft server (confirmed behavior of the existing single-API-key flow today, unchanged by this spec) — this is not new error-handling code, just confirmation the existing mod behavior covers this path.
- Dropdown writes use the same write path as the existing API key field, so failure modes (e.g. config file locked/unwritable) are identical to today's existing behavior — no new handling needed.

## Testing

- Unit test `Set-VerityRemoteFallback`: given an old-schema file with a sidecar set to remote-incompatible provider, assert it's flipped; given a new-schema file with `use_ollama = $true`, assert it's flipped to `$false`; given a missing/unwritable file, assert no throw.
- Unit test the fallback fix's call site is reached on sidecar-start failure (extend existing sidecar-start-failure test coverage if present, or add coverage matching the pattern of existing `Start-*Sidecar` tests).
- No new tests for the dropdowns' XAML wiring — matches the project's existing pattern of testing helpers, not XAML interaction (same rationale as the Address Display spec).

## Decisions Made

- New-server default is already remote/cloud via the mod's own factory config — no launcher-side change needed for that; confirmed with the user before writing this spec to avoid building unnecessary post-processing logic.
- Fallback auto-flips to remote (not a hard block) — matches the existing warning message's claim and keeps the server startable even when local AI fails.
- No block on missing API key + failed local sidecar — server starts, Verity's own AI features degrade, matching how a missing key already behaves today in remote mode.
- Remote provider choice is a curated dropdown of the mod's documented `aiProvider` values, not free text — no guardrail needed since these are exactly the mod's allowed values already.
- Local model choice is a curated dropdown, ships with one entry for this release — avoids exposing arbitrary Ollama model pulls (no guardrail against hardware-inappropriate or Verity-incompatible models) while leaving room to expand later.
- TTS/STT get no provider dropdown — the mod only supports one remote option (`NATIVE`) for each, so the existing local/remote toggle is already the complete choice.
